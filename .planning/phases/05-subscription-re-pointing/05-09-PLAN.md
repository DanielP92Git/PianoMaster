<objective>
Touch the live subscriptions — for the first time in this phase, and only now, because SC-4 requires
sandbox verification to pass first and plan 05-08 has recorded `SANDBOX PASS`.

Three things happen here, in a strict order that cannot be rearranged: the migration is applied and
verified, the 3 real customers' rows are signed off individually, and the Edge Functions are deployed
so the new column actually gets written. Deploying before the apply would make the webhook write to a
column that does not exist; applying without deploying would leave new subscriptions invisible to a
client that now reads `parent_id`.

Purpose: SC-1's production reality and SC-2 in full.
Output: the completed D-11 sign-off doc and the production half of `05-apply-log.md`.

## Hard preconditions (enforced by Task 0, not by reading)

1. `05-sandbox-log.md` contains `SANDBOX PASS` and does not contain `SANDBOX FAIL`.
2. `05-apply-log.md` contains `REHEARSAL PASS` and does not contain `REHEARSAL FAIL`.
3. **DEPLOY-GATE (see 05-05):** the phase branch has NOT been merged to `main` / deployed to Netlify
   production. `origin/main` must not yet carry `eq("parent_id"` in
   `src/services/subscriptionService.js`. Deploying the client before Task 1 applies the migration
   makes every `parent_subscriptions` query error and drives `fetchSubscriptionStatus` into its
   fail-closed branch for **all 3 live paying customers at once**. If the gate finds the code already
   on `main`, that incident is live: revert `main` first, then proceed.

The gate is released — and merging to `main` becomes safe — only when **Task 3** writes the literal
line `frontend_deploy_gate: RELEASED` into `05-apply-log.md`, which it does only after the migration
is applied (Task 1) and all four Edge Functions are deployed (Task 3). Ordering is therefore:
migration → Edge Functions → frontend merge. Never the reverse.
</objective>
