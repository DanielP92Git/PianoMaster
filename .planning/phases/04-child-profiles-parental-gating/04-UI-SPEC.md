## Typography

| Role    | Size | Weight         | Line Height |
| ------- | ---- | -------------- | ----------- |
| Body    | 16px | 400 (regular)  | 1.5         |
| Label   | 14px | 600 (semibold) | 1.4         |
| Heading | 20px | 600 (semibold) | 1.2         |
| Display | 28px | 600 (semibold) | 1.15        |

**2-weight declaration:** 400 (regular) for body copy, helper text, and data-rights descriptions; 600 (semibold) for labels, section/screen headings, and all button text. **Locked exception:** `ParentGateMath`'s existing math-problem numeral (`text-4xl font-black`, i.e. 36px/900) is inherited **unchanged** — it is a reused, locked component (D-06 lifts its pass-state, does not restyle it), not a new weight introduced by this phase.

- Body → nickname helper text, deactivate/delete/export descriptive copy, empty-state body
- Label → form field labels, switcher avatar name captions, list-row metadata (e.g. "Last played 2 days ago")
- Heading → "Who's playing?" overlay title, per-child panel section headers ("Profile", "Data & Privacy"), gate modal title
- Display → "Manage Children" page-level title, "Add your first child" empty-state heading

Accent reserved for: primary CTA fills, active-child selection rings, and focus states only — never for large surface fills, list-row backgrounds, or default (unselected) switcher tiles. The Amber/Red split is the load-bearing color decision of this phase: it is what makes "Deactivate" visually read as safe-and-reversible and "Delete" visually read as serious-and-final, satisfying the phase brief's "parent surfaces should read clearly adult/serious" requirement specifically for the two destructive-adjacent actions.

## Visual Hierarchy (per surface)

- **"Who's playing?" switcher overlay:** The sibling avatar tiles + "Add" tile are the sole focal point — large, evenly spaced, kid-legible. No secondary chrome competes (no settings icon, no gate hint visible on this screen — it is deliberately ungated per D-07).
- **Parental gate modal:** The math problem is the focal point (unchanged, inherited from `ParentGateMath`); the surface it is fronting is invisible/blocked behind it until solved. Cancel is secondary/ghost.
- **Manage Children screen:** The list of children is the focal point on entry; drilling into a child makes that child's panel (rename/avatar/rename → then Data & Privacy) the focal point, with Deactivate/Delete visually demoted below the review/export actions (never the first thing seen).
- **Create/edit child form:** The nickname field and avatar grid are the two focal points, in that order top-to-bottom; the full-name warning (when triggered) is secondary and must never visually compete with or block the Save button.
- **Data-rights actions (deactivate/delete):** Deactivate reads calm (amber, reversible framing, "you can turn this back on"); Delete reads serious (red, permanent framing, name-confirmation gate) — the two must never share visual weight or placement that implies interchangeability.
- **Parent Portal (split, D-08):** Read-only stats (Quick Stats grid, heatmap) are visually unguarded and load immediately; action rows (subscription, notifications) are visually marked as requiring the gate (e.g. a small lock affordance) even before the gate is invoked, so a child browsing the portal understands why those rows don't respond to a tap.

## Phase-Specific UI Notes (beyond template, for executor reference)

### 1. "Who's playing?" switcher overlay (D-01/D-02/D-03/D-07)

- Entry point: the existing 48px avatar in `Header.jsx` (`h-12 w-12 rounded-full ring-2 ring-white/20`) — change its click target from `<Link to="/avatars">` to open the overlay; do not restyle the entry-point avatar itself.
- Overlay: `fixed inset-0` glass panel (`bg-black/60 backdrop-blur-sm` scrim + `bg-white/10 backdrop-blur-md border-white/20 rounded-xl` content card, matching `ParentGateMath`'s existing scrim/card pattern) — reuse that exact scrim treatment rather than inventing a new one.
- Grid of 72px circular sibling tiles + one "Add" tile (dashed-border variant of the same tile, indigo accent icon, e.g. `UserPlus` from lucide-react), each tile captioned with the child's nickname in Label typography below it.
- The currently-active child's tile gets the Accent-color selection ring (indigo-400); all others are unselected/neutral.
- **Fully ungated in both directions (D-07)** — no math gate anywhere on this overlay, including switching to a different child. Tapping "Add" is the one path that DOES route through the gate (into the create-profile flow, D-03) — the overlay itself, and switching away from a child, are not gated.
- Zero-child state: no sibling tiles, just the "Add" tile plus the empty-state heading/body from the Copywriting Contract.

### 2. Parental gate — presentation (D-05/D-06/D-08)

- Visual mechanism unchanged: `ParentGateMath`'s existing glass modal (`bg-black/60` scrim, `bg-white/10 backdrop-blur-md border-white/20 rounded-xl` card, 4xl/font-black numeral) — do not redesign it.
- **Generalize its copy/i18n keys** off the notification-specific namespace (see Copywriting Contract) since it now fronts four different surfaces (Manage Children, Settings, Subscription/Billing, Portal actions), not just push-notification opt-in.
- No new "shared window is open" chrome is required on the gated screens themselves — the window is invisible plumbing (D-06, in-memory only). The only new visible state is: gate modal shown (not passed) vs. gate modal absent (passed, within window) vs. gate modal shown again (window expired/closed) — same modal, same visual treatment, every time.
- Parent Portal split (D-08): visually mark gated action rows (subscription management, notification settings) with a small lock/shield glyph (reuse `ShieldCheck` or `Lock` from lucide-react, already imported in `ParentPortalPage.jsx`) so a child browsing the now-ungated read-only stats understands why those rows don't respond, without needing to trigger the gate to find out.

### 3. "Manage Children" screen (D-09)

- New gated route. Standard glass page shell (`bg-white/10 backdrop-blur-md border-white/20 rounded-xl`) on the app's purple-gradient background, with `BackButton` (existing component) at the top — mirrors `ParentPortalPage`'s existing page-shell conventions.
- List view: one glass row per child (avatar, nickname, "active"/"paused" status badge — reuse the `StatusBadge`-style pill pattern already in `ParentPortalPage.jsx`), each row navigates into that child's panel.
- Per-child panel: two sections in Heading typography — "Profile" (rename, avatar picker) and "Data & Privacy" (Review Data, Download, Pause/Turn Back On, Delete) — Data & Privacy's destructive actions (Delete) sit visually last/lowest, never adjacent to or styled like the primary Save action.
- Paused/deactivated children still appear in this list (with a "Paused" badge and a "Turn Back On" action) — they only disappear from the ungated "Who's playing?" switcher (D-10).

### 4. Compact preset-avatar picker (D-13)

- Inline grid inside the create/edit form only — 56px circular tiles, reading the DB `avatars` set (`apiAvatars.getAvatar()`, existing `["avatars"]` query — do not build a new catalog query).
- Selected tile gets the Accent indigo ring; unselected tiles are neutral glass (`bg-white/5 border-white/10`).
- No accessory layering, no upload affordance, no "Beethoven/Bach/..." composer-name treatment from `Avatars.jsx` — this is a plain preset grid, visually simpler than the full Avatars page it must NOT reuse.

### 5. Child create/edit form (D-13/D-14/D-15)

- Standard glass form card. Field order top-to-bottom: nickname input → helper text (always visible, Body/regular) → avatar grid → Save button.
- The full-name warning (Amber) appears directly beneath the nickname field, above the avatar grid, only when the heuristic triggers — it must never disable or visually block the Save button (D-14 is non-blocking by contract).
- On successful create, auto-switch into the new child and land on their dashboard (D-15) — no confirmation toast is required before the switch; the dashboard itself is the confirmation.

### 6. Data-rights actions (D-10/D-11/D-12)

- **Deactivate ("Pause Profile"):** Amber-toned inline confirmation (can be a lightweight inline expand, not necessarily a full modal — planner's call) using the Copywriting Contract's confirm copy. No name-typing required (this is reversible).
- **Delete ("Delete Profile"):** Full modal, red-toned, following `AccountDeletionModal`'s exact structure (warning banner → what-will-be-deleted summary → name-confirmation input matching the child's nickname case-insensitively → disabled-until-match "Delete Forever" button) — reuse that component's visual pattern, adapted to per-child copy and dropping the 30-day-grace-period language (D-12: this delete is immediate, no grace period; deactivate is the reversible lever instead).
- **Export/Review:** A simple "Download My Child's Data" action that triggers the existing `downloadStudentDataJSON` flow (button + loading spinner state, no bespoke screen needed) — "Review Data" may reuse the same underlying export call rendered as an on-screen summary rather than a raw-JSON view (planner's discretion per CONTEXT.md).

### 7. Parent Portal split (D-08)

- Quick Stats grid + practice heatmap: remove their `enabled: !!user?.id && !gateOpen` gating — these become always-visible once a child is loaded (ungated read-only viewing).
- Subscription management + notification settings sections: keep gated, now behind the shared `ParentGateContext` rather than the page's local `gateOpen` state — visually mark with the lock glyph per note 2 above.
- The Privacy Policy link (carried over from Phase 3 SIGNUP-05) lands in this screen's parent-settings area, styled exactly like Phase 3's existing entry-screen treatment (`text-white/75 underline hover:text-white`, opens `/privacy` in a new tab).
